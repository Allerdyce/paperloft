## What was wrong and what changed

The first run, on the harness commit `c4a61f6` (`parser-20261001T220135Z`), took 27.1 s but stalled the main thread for 498 ms. The first system run (`system-20261001T223053Z`, after the review fix below) took 371 s and 370 s but stalled for 258 ms late in the measured iteration.

Diagnosis used intrusive tools only, never as timing evidence:
- native sampling (`evidence/pipeline-stacks-20261001T220257Z`)
- Instruments Time Profiler hang tables (`parser-…220613Z`, `parser-…221900Z`, `system-…224444Z`)
- an lldb breakpoint that logged the object asked for its baseline (`parser-…221321Z`)

1. **Opening a document for review (about 0.6 s).** SwiftUI asked each review pop-up (currency, category, document type) for its text baseline on every layout pass: 1,568 times in one run, and each answer re-entered window layout. The review pane also rebuilt its split view, preview and fields for every document.
   - **Fix:** the pop-ups state their baseline and cache their measured size. `ReviewSplitView` keeps the split view and preview while you move between documents, and only the fields column is keyed to the document. On first appearance, the fields follow the preview one frame later.
   - **Trial runs:** `221101Z`, calendar-button guide, no effect. `221757Z`, pop-up baselines, 436 ms. `222041Z`, plus the size cache, 421 ms. `222314Z`, first-time-only staging, 245 / 381 ms. `222630Z`, persistent split view, 226 / 207 ms.
2. **Inbox refresh after each document (about 200 ms late in a system run).** Every refresh checks each row's status for the list and the five filter chips. Each check built `Money`, and `Money` created a new `NumberFormatter` to look up the currency's decimal places. That accounted for 1,815 of 3,068 refresh samples.
   - **Fix:** `Money` looks the decimal places up once per currency code, with unchanged validation.
