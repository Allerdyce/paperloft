## Why the 429 s run (and probably the owner's 10-02 run) was slow

The 429 s run came first, so it looked like a regression since the 10-01 runs (369 s on `c2f7ad0`). The same session then ran a bisect, one system run per commit, in detached worktrees (`paperloft-perf` at `c2f7ad0`, `paperloft-bisect` for the rest; raw logs in their ignored `build/`):

| Commit | Iteration 1 |
| --- | --- |
| `c2f7ad0` (the 10-01 harness commit) | 367.2 s |
| `7cd0f79` | 361.6 s (its first heartbeat gap was 259 ms at 0.26 s after launch; not seen in any other run) |
| `44a995e` | 365.7 s |
| `1a83e7d` | 365.6 s |
| `cec2b50` (HEAD), rerun | 366.9 s / 366.0 s |

There's no code regression. Between `1a83e7d` and HEAD the only app change is `restoreRemoved` (Undo of a removal), which the test never calls. The one slow run was the first after the Mac had been idle. That points to a cold start (on-device model and system caches) or background work at that moment. That's an inference, not a measured cause. The owner's 10-02 run (520 s cutoff, 88/100) had `mediaanalysisd` at about 250% CPU on top of that.

**For the owner's Terminal run:** use a Mac that has been awake and in use for a few minutes, with no Photos or Spotlight indexing running. If the system run fails on time anyway, run it once more; the gate reads the newest folder.

100/100 completed and persisted on the system backend in both iterations, with no failures, and XCTest passed. XCTest recorded Clock Monotonic Time (360.4 s) and Memory Peak Physical (355 MB), but **again no UnderstandInboxBatch signpost**, even from Terminal.

**Revised diagnosis.** The cause is probably not the shell's unified-log access. Every performance run so far, from the agent's shell and from Terminal, logs `NSCocoaErrorDomain Code=4097 "connection to service named com.apple.metricmeasurement.MetricMeasurementHelper"` from the app process. It appears once per measured iteration, at the moment the iteration ends, which is when XCTest collects signpost data. The performance tests are hosted in the sandboxed app (`TEST_HOST` is Paperloft Receipts), so the likely blocker is the App Sandbox stopping the app from reaching XCTest's metric helper. Clock and memory metrics are measured in-process and don't need it. This is a hypothesis until an experiment confirms it.

The `MDB_MAP_FULL` lines in the 10-08 rerun and this run come from a system cache, not Paperloft code. The passing 366 s run logged 194 of them, so they don't affect timing.

## 2026-10-09: signpost probe (no app, no sandbox)

`build/signpost-probe` (ignored; a minimal Swift package) measures one 0.5 s OSSignposter interval with `XCTClockMetric` and `XCTOSSignpostMetric` under `swift test`. Run from the agent's shell and from the owner's Terminal, it recorded only Clock Monotonic Time (0.497 s), with no signpost. So on this Mac, neither shell can collect signpost metrics even outside the App Sandbox. Unified-log access is the first blocker (`log show`: "Could not open local log store: Operation not permitted" in the agent's shell; this account is a Standard user). The app's sandbox may be a second blocker (the 4097 `MetricMeasurementHelper` failures); that can only be tested once a shell can collect the probe's signpost.
