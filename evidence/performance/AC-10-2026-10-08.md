## Why the 429 s run (and probably the owner's 10-02 run) was slow

The 429 s run came first, so it looked like a regression since the 10-01 runs (369 s on `c2f7ad0`). The same session then ran a bisect, one system run per commit, in detached worktrees (`paperloft-perf` at `c2f7ad0`, `paperloft-bisect` for the rest; raw logs in their ignored `build/`):

| Commit | Iteration 1 |
| --- | --- |
| `c2f7ad0` (the 10-01 harness commit) | 367.2 s |
| `7cd0f79` | 361.6 s (its first heartbeat gap was 259 ms at 0.26 s after launch; not seen in any other run) |
| `44a995e` | 365.7 s |
| `1a83e7d` | 365.6 s |
| `cec2b50` (HEAD), rerun | 366.9 s / 366.0 s |

There's no code regression. Between `1a83e7d` and HEAD the only app change is `restoreRemoved` (Undo of a removal), which the test never calls. The one slow run was the first after the Mac had been idle. That points to a cold start (on-device model and system caches) or background work at that moment. That's an inference, not a measured cause. The owner's 10-02 run (520 s cutoff, 88/100) had `mediaanalysisd` at about 250% CPU on top of that.

**For the owner's Terminal run:** use a Mac that has been awake and in use for a few minutes, with no Photos or Spotlight indexing running. If the system run fails on time anyway, run it once more; the gate reads the newest folder.
